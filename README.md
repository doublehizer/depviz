# Визуализатор графа зависимостей NuGet

Практическая работа № 2 по дисциплине «Конфигурационное управление»,
вариант 12.

## Общее описание

Консольное приложение (CLI), которое строит граф зависимостей пакета
менеджера пакетов .NET (NuGet). Готовые менеджеры пакетов и библиотеки
для получения зависимостей не используются.

Текущий этап — **этап 3 (основные операции)**. Приложение читает
YAML-файл настроек, проверяет все параметры и строит **полный граф
зависимостей** (с транзитивными) обходом в глубину: из настоящего
репозитория NuGet или из файла тестового репозитория.

- Если в настройках есть ошибки, выводятся **все** найденные ошибки
  сразу, а код выхода равен 1.
- Вывод всех параметров `ключ = значение` был нужен только на этапе 1,
  а вывод прямых зависимостей — только на этапе 2 (так сказано
  в задании). С этапа 3 выводится граф.

## Параметры (файл настроек)

Настройки задаются в YAML-файле. Все параметры обязательные.

| Параметр | Тип | Описание | Ошибка, если |
|---|---|---|---|
| `package` | строка | имя анализируемого пакета | пусто; есть символы кроме латинских букв, цифр, `.`, `_`, `-` |
| `repository` | строка | URL репозитория или путь к файлу тестового репозитория | пусто |
| `test_mode` | `true`/`false` | режим работы с тестовым репозиторием | не логическое значение |
| `output_image` | строка | имя файла с изображением графа | пусто; не оканчивается на `.png` |
| `ascii_tree` | `true`/`false` | выводить зависимости ASCII-деревом | не логическое значение |
| `max_depth` | целое | максимальная глубина анализа | не целое число; меньше 1 |
| `filter` | строка | подстрока для фильтрации пакетов, `""` — без фильтра | не строка |

Дополнительные проверки:

- лишний параметр — ошибка `неизвестный параметр`;
- пропущенный параметр — ошибка `параметр не задан`;
- обычный режим (`test_mode: false`): `repository` должен быть URL
  со схемой `http` или `https`;
- тестовый режим (`test_mode: true`): `repository` — путь к
  существующему файлу (считается от папки файла настроек), а имя
  пакета состоит из больших латинских букв (`A`, `B`, ...);
- файл настроек не найден, ошибка синтаксиса YAML (с номером строки),
  в файле не пары `ключ: значение` — тоже ошибки.

Пример файла настроек (`config.yaml`):

```yaml
package: Serilog.Sinks.Console
repository: https://api.nuget.org/v3/index.json
test_mode: false
output_image: graph.png
ascii_tree: true
max_depth: 3
filter: ""
```

## Как получаются зависимости (этап 2)

Менеджеры пакетов и библиотеки NuGet не используются: только HTTP
(`urllib`) и разбор JSON/XML из стандартной библиотеки Python.
Параметр `repository` — адрес списка сервисов репозитория NuGet v3,
например `https://api.nuget.org/v3/index.json`.

1. **Список сервисов.** Скачивается `index.json`, в нём ищется адрес
   хранилища пакетов — ресурс типа `PackageBaseAddress/3.0.0`
   (для nuget.org это `https://api.nuget.org/v3-flatcontainer/`).
2. **Версия.** Скачивается список версий пакета
   `<хранилище>/<имя>/index.json` и выбирается последняя стабильная
   (без `-beta`, `-rc` и т.п.). Версии сравниваются по числам:
   `1.2.10` новее `1.2.9`.
3. **Описание пакета.** Скачивается файл
   `<хранилище>/<имя>/<версия>/<имя>.nuspec` — это XML с описанием
   пакета. Из него берутся элементы `<dependency id="…" version="…">`.

### Группа зависимостей net8.0

Один пакет NuGet может поддерживать несколько версий .NET, и для
каждой у него свой список зависимостей — **группа** (`<group
targetFramework="…">`). Например, у пакета могут быть группы
`.NETFramework4.6.2`, `net6.0`, `net8.0`, `.NETStandard2.0`.

**net8.0** — это .NET 8, текущая версия .NET с долгосрочной поддержкой
(LTS). Инструмент считает, что пакет подключается к проекту на net8.0,
и берёт **одну** группу — так же, как это делает настоящий NuGet:

1. группа `net8.0`, если она есть;
2. иначе ближайшая совместимая: `net7.0`, `net6.0`, `net5.0`,
   `netcoreapp3.1` … `netcoreapp1.0`, `netstandard2.1` …
   `netstandard1.0`;
3. иначе группа без указания фреймворка (старый формат .nuspec,
   где зависимости перечислены без групп).

Группы для более новых версий (`net9.0`, `net10.0`) и для старого
.NET Framework (`.NETFramework4.x`) с net8.0 не совместимы и не
берутся. Если совместимой группы нет, об этом выводится сообщение.

### Ошибки получения данных

| Ситуация | Сообщение |
|---|---|
| сервер недоступен, нет сети | `не удалось подключиться: …` |
| пакета нет (ответ 404) | `пакет … не найден в репозитории` |
| адрес не репозиторий NuGet | `ответ не в формате JSON: …` или `в репозитории нет сервиса PackageBaseAddress/3.0.0` |
| у пакета нет версий | `у пакета нет ни одной версии` |
| `.nuspec` не XML | `описание пакета .nuspec не в формате XML` |

## Построение графа (этап 3)

Граф строится **рекурсивным обходом в глубину (DFS)** — модуль
`graph.py`, метод `GraphBuilder.visit`: функция обрабатывает пакет,
берёт его прямые зависимости и вызывает саму себя для каждой из них.

- **Глубина (`max_depth`).** У корня глубина 0, у прямых зависимостей
  1 и т.д. Пакет на глубине `max_depth` попадает в граф, но его
  зависимости уже не запрашиваются (в выводе — пометка
  `… достигнута max_depth`).
- **Фильтр (`filter`).** Пакет, в имени которого есть подстрока
  (без учёта регистра), не попадает в граф, и его зависимости
  не анализируются. Пустая строка — без фильтра. Корневой пакет
  анализируется всегда.
- **Циклы.** Обход помнит **текущий путь** (стек). Если зависимость
  уже на пути — это цикл: ребро запоминается и выводится в строке
  «Циклы», но второй раз в пакет не заходим, поэтому обход
  не зацикливается.
- **Общие зависимости («ромб»).** `A → B → D` и `A → C → D` — это
  **не** цикл: `D` раскрывается один раз и повторно не запрашивается.
- **Короткий путь важнее.** Если до пакета сначала дошли длинным путём
  (и обрезали по глубине), а потом коротким — пакет раскрывается
  заново, чтобы ограничение глубины не потеряло зависимости, которые
  в него помещаются.

### Версии транзитивных зависимостей (NuGet)

- корневой пакет — последняя стабильная версия (как на этапе 2);
- зависимость — **самая низкая версия, подходящая под диапазон** из
  `.nuspec` пакета, который первым на неё сослался; так версии
  выбирает и сам NuGet. Диапазоны: `4.0.0` — 4.0.0 и новее,
  `[8.0.0, 9.0.0)` — от 8.0.0 до 9.0.0 не включая, `[1.0]` — ровно 1.0;
- группа зависимостей — net8.0 или ближайшая совместимая (как на этапе 2);
- каждый пакет скачивается один раз (ответы запоминаются).

### Тестовый репозиторий (`test_mode: true`)

Вместо URL указывается путь к текстовому файлу, где пакеты названы
большими латинскими буквами. Одна строка — один пакет:

```
# комментарий
A: B C
B: D
C: D E
D:
E: A
```

Слева от двоеточия — пакет, справа через пробел — его прямые
зависимости. Пакет без зависимостей записывается как `D:`. Каждый
упомянутый пакет должен быть описан своей строкой.

Ошибки файла (с номером строки): нет двоеточия, имя не из больших
латинских букв, пакет описан дважды, пакет упоминается, но не описан;
а также: файла нет, анализируемого пакета нет в репозитории.

## Структура проекта

```
src/depviz/
    __main__.py   запуск через python -m depviz
    main.py       точка входа: настройки → источник → граф → вывод
    config.py     чтение и проверка YAML-файла настроек
    graph.py      построение графа обходом в глубину (DFS)
    nuget.py      зависимости из репозитория NuGet (NuGetSource)
    testrepo.py   тестовый репозиторий из файла (TestRepository)
    errors.py     классы ошибок ConfigError, NuGetError, RepoFileError
tests/
    test_*.py     автотесты (unittest)
    configs/      примеры файлов настроек: правильные и с ошибками
    configs/stage3/  настройки для случаев тестового репозитория
    nuget/        примеры ответов NuGet для тестов без интернета
    repos/        файлы тестовых репозиториев
    stage1/       скрипт демонстрации этапа 1 (ошибки настроек)
    stage2/       скрипт демонстрации этапа 2 (настоящий NuGet)
    stage3/       скрипты демонстрации этапа 3 (граф)
config.yaml       пример настроек
requirements.txt  зависимости (PyYAML)
run.sh            скрипт запуска
```

## Сборка и запуск

Нужен Python 3.9+. Единственная сторонняя библиотека — PyYAML (только
для чтения файла настроек). Сборка не требуется: при первом запуске
`run.sh` сам создаёт окружение `.venv` и ставит туда PyYAML.

Запуск:

```sh
./run.sh
./run.sh --config tests/configs/test_mode.yaml
```

Запуск автотестов:

```sh
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -v
```

Автотесты не обращаются к интернету: ответы сервера подменяются
файлами из `tests/nuget/` и заготовленными данными.

Демонстрация этапа 3 на тестовом репозитории (без интернета):

```sh
tests/stage3/demo.sh
```
